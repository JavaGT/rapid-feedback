## Findings (ranked strength x leverage)

### 1. STRONG — AGENTS.md run-all paragraph is stale on two counts (docs contradict code)
- AGENTS.md:8 says "test/run-all.js wires the eight suites: test/run.js plus
  test/run2.js–test/run8.js (no run1.js)". test/run9.js now exists and
  test/run-all.js:1 wires NINE suites (run, run2–run8, run9). "no run1.js" is
  still true; the count is not.
- Same sentence: "override the Chrome binary with RAPID_FEEDBACK_CHROME". Commit
  533c7bd added RAPID_FEEDBACK_BROWSER and RAPID_FEEDBACK_EXECUTABLE
  (test/common.js:6-9); RAPID_FEEDBACK_CHROME is now only a legacy fallback for
  the executable. The doc names the deprecated knob and omits the two live ones.
- Leverage: one-line doc fix each; AGENTS.md is the onboarding doc for agents.
- Adjacent drift (same commit, README.md:91): run9 is described as "the
  click-through targeting regression in Firefox", but run9 is an ordinary suite
  that run-all runs under Chrome; Firefox is opt-in via env vars, not a property
  of the suite.

### 2. MEDIUM-HIGH — Coordinate guard (2aed5bf) misses the finite-but-bogus (0,0) case, and has zero test coverage
- rapid-feedback.user.js:2775 guards `Number.isFinite(e.clientX/clientY)`, which
  filters NaN/undefined only. Synthetic and keyboard-activated clicks
  (`el.click()`, Enter on a button, `new MouseEvent('click', {ctrlKey:true})`)
  carry clientX=0, clientY=0 — finite, so the guard passes and
  inspectionElementsAt hit-tests the viewport top-left corner. resolveChordTarget
  then retargets the annotation/outline to whatever paints at (0,0) instead of
  the event target (loop at :2776-2787 breaks on the first acceptable element).
- Three call sites exposed: openChordAnnotation :2810, addToChordGroup :2837
  (multi-select accumulate), chord-hover outline :2986.
- Pre-533c7bd this path only hit-tested pierce-layer targets, so synthetic clicks
  on ordinary elements kept their target; the broadened hit-test made (0,0) a new
  failure mode. 2aed5bf closed NaN/undefined but not the spec-default zeros.
  Possibly overlaps #50 ("targeting boundaries") — flagging as distinct because
  #50 is scoped to cost/targeting of the inspection pass.
- Coverage: no suite dispatches coordinate-less or synthetic chord clicks (grep
  across test/run*.js: no clientX/clientY/isFinite/synthetic chord click), so the
  guard that 2aed5bf landed is untested either way.

### 3. MEDIUM — No fallback through the elementsFromPoint stack when the top pick is an empty decoration
- rapid-feedback.user.js:2754 forces `* { pointer-events: auto !important; }`
  during inspection, and the loop at :2776-2787 `break`s on the first painted
  element that is not a pierce layer / RF chrome / body/html. Small
  pointer-events:none decorations (shimmer spans, gradient overlays, empty
  spacers) now win the pick over the interactive element beneath them.
- isOverlayShell (:2735-2746) only filters ~viewport-sized shells (:2741 width /
  height >= 0.9 * viewport), so a 40px empty overlay is picked. getTextSnippet
  (:418-421) then returns '' and the annotation captures an empty-text element.
- This is the inverse of #48 (hint-under-editor) and a deliberate tradeoff per
  the comment at :2748-2751 ("Inspection targets painted elements"), but there is
  no second-chance: the remaining elements in the elementsFromPoint list are
  discarded even when the winner has no text and the element beneath does.
  Possible overlap with #50 boundaries; the empty-text capture path itself is
  unticketed as far as the scoped list shows.

### 4. LOW-MEDIUM — common.js env-var precedence can hand Firefox a Chrome binary
- test/common.js:6-9: `EXECUTABLE = ...RAPID_FEEDBACK_EXECUTABLE ||
  RAPID_FEEDBACK_CHROME || (BROWSER === 'firefox' ? firefox : chrome)`. With
  RAPID_FEEDBACK_BROWSER=firefox and a leftover RAPID_FEEDBACK_CHROME set (the
  documented knob in AGENTS.md:8), puppeteer launches Firefox with the Chrome
  path — a confusing failure far from the cause. Precedence should be
  browser-aware (legacy var only honored when it matches BROWSER).

### 5. LOW — @note header ordering drift (533c7bd)
- rapid-feedback.user.js:4-19: v5.19 note inserted between @version and
  @description (line 5), while the note list below reads v5.16, v5.18, v5.17,
  v5.14... — never in version order, and the new note is separated from the list
  by @description. Cosmetic, but every release compounds it.

### 6. INFORMATIONAL
